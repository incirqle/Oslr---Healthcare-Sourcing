# AGENTS.md

- Unlimited contact passes are authorized only by `billing_exemptions.unlimited_access` read server-side after resolving the caller's workspace; ordinary billing exemptions remain credit-metered. Why: permanent free lookup access must not rely on client flags, admin roles, or a finite credit grant.

- Per-criterion results and the match rate are computed server-side in `supabase/functions/_shared/clinician-engine/ranking-criteria.ts` (rules first, the grader only for what rules leave); the browser only joins criterion titles and renders. Why: one scoring source shared by tests, cards and the later table view.
- Live re-ranking in the browser (reorder, must-have, remove) goes through `src/lib/ranking.ts`, a straight port of the server's `scoreRow`; it only re-weights per-criterion results the server returned. Why: instant changes with no request, one formula on both sides.
- Checking added or edited criteria (`rank_criteria`) and explanations (`explain_criteria`) live in `_shared/clinician-engine/rank-actions.ts` (pure, injected deps) and `rank-route.ts` (cache + grader wiring); they read only the run snapshot cached under `clin:run:<run_id>` and must never import the people-data provider. Why: zero provider credits, enforced by rank-actions.test.ts.
- Oslr Agents live in `supabase/functions/clinician-agent` (user actions) and `agents-tick` (hourly scheduler); shared logic is `_shared/agents/agent-brain.ts` (pure learning, tested) and `agent-core.ts` (sourcing through the in-process clinician search, AI memo). Access is gated server-side by `company_features.plan` or an approved `agents_enabled` switch. Why: one search engine and one learning formula for live and scheduled runs, with access the browser cannot bypass.
- Scheduled agent runs authenticate to the clinician search with the service key plus `x-oslr-internal-user`, honored only inside `resolveCaller`. Why: nightly runs have no user session but must still be metered to the agent owner.
- The public marketing site lives in `src/marketing`: each route renders the exported page HTML from `src/marketing/pages`, with `/site/assets/css/oslr.css` attached only while a marketing page is mounted and `/site/assets/js/oslr.js` run after mount. Links between marketing pages are plain anchors (full page loads). Marketing paths avoid app paths: products sit under `/product/*`, guides under `/guides/*`. Why: the site ships pixel-for-pixel as designed without its global styles leaking into the app.
- New checkouts use the Oslr Stripe account (`STRIPE_OSLR_SECRET_KEY`); workspaces with a live plan on the legacy Pitchsink account (`STRIPE_SECRET_KEY`) stay there for status, portal and upgrades. Why: Oslr branding for new buyers without breaking existing subscriptions.
- Plan prices, monthly credits, Stripe price ids and per-plan contact costs live only in `supabase/functions/_shared/plans.ts`; billing `status` writes the plan to `company_features.plan` (and turns Agents on for Pro), and contact lookups read it server-side. Why: one source for what each plan pays and gets.
- Monthly credits are granted through `reset_monthly_credits` (balance set to the month's allowance, leftovers logged as expired); yearly plans grant one month at a time keyed by month index. The invite-only early-access price is allowed at checkout only for emails in `beta_plan_invites`. Seat limits are enforced by a database trigger on `company_invites`. Why: no rollover, no upfront yearly credits, and limits the browser cannot bypass.
- Credits are one shared pool per workspace, never per user. Billing computes the monthly pool from seats in use (`creditsForSeats` in `plans.ts`), and a trigger on `profiles` grants the per-seat amount when a member joins a workspace whose plan pools per seat. Why: the pool must grow the moment a seat is added and the browser can never set the amount.
- Agent creation uses `create_metered_clin_agent` with an idempotent request UUID; a database trigger serializes workspace capacity checks, insert charges, and resume checks. Only calibrating/sourcing agents occupy slots; paused/completed/closed agents do not. Why: concurrent requests cannot exceed limits or spend the shared balance twice, and project creation rolls back with a rejected agent.
- Agent brief previews reuse the clinical parser and its cache without invoking sourcing; the validated parse is pinned to its exact brief in agent preferences and supplied to scheduled searches. Natural-language rules are validated in `agent-language.ts` and feed the same deterministic reranker; conversational resumes pass through the existing database cap trigger. Why: previews cannot consume search/contact credits, searches do not drift, and chat cannot bypass capacity.
